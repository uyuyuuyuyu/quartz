# 1. Why Side-Channel Attacks Matter

Modern cryptographic algorithms such as **AES and RSA are mathematically strong**.

The main problem is often not the algorithm itself, but its **implementation on a physical device**.

> [!important]
> **Implementation attacks do not attack weaknesses in the cryptographic algorithm. They attack information leaked by its implementation.**

When a device processes sensitive data, it unintentionally produces physical effects.

Examples:

- Power consumption
- Electromagnetic (EM) radiation
- Execution time
- Acoustic emissions
- Light emissions
- Substrate noise

These effects may depend on:

- Secret keys
- Secret intermediate values
- Operations executed
- Memory addresses accessed

Therefore:

$$
\text{secret-dependent computation}
\rightarrow
\text{observable leakage}
\rightarrow
\text{possible key recovery}
$$

---

# 2. Side-Channel Attack Workflow

The general workflow is:

$$
\text{Trace Measurement}
\rightarrow
\text{Pre-processing}
\rightarrow
\text{Leakage Identification}
\rightarrow
\text{Leakage Exploitation}
\rightarrow
\text{Key Recovery}
$$

### Step 1 - Trace measurement

Collect physical measurements from the device.

Examples:

- Power traces
- EM traces
- Timing measurements

### Step 2 - Pre-processing

Prepare traces for analysis.

Examples:

- Alignment
- Filtering
- Noise reduction
- Resynchronization

### Step 3 - Leakage identification

Find **where in the trace sensitive information is leaking**.

### Step 4 - Leakage exploitation

Use the detected leakage to infer secret information.

---

# 3. Three Types of Side-Channel Analysis

## 3.1 Simple SCA

Example:

- Simple Power Analysis (SPA)
- Simple EM Analysis (SEMA)

The attacker directly looks at a trace and identifies patterns.

Example: RSA square-and-multiply.

For each exponent bit:

- Always perform **square**
- If bit = 1, also perform **multiply**

Conceptually:

$$
k_i=0 \Rightarrow \text{Square}
$$

$$
k_i=1 \Rightarrow \text{Square + Multiply}
$$

If square and multiply have visibly different power signatures, the key bits can be recovered directly.

---

## 3.2 Non-Profiled SCA

The attacker does **not** have a training/clone device.

Instead, they:

1. Guess possible secret values.
2. Predict the leakage caused by each guess.
3. Compare predictions against measured traces.

Common tools:

- Difference of Means (DoM)
- Pearson correlation
- Mutual information

A major example is:

**Correlation Power Analysis (CPA)**

---

## 3.3 Profiled SCA

The attacker has access to a **training/clone device** where the key can be controlled.

They first learn how the device leaks information.

Then they use this learned model against the victim device.

Common approaches:

- Template attacks
- SVM
- Random Forest
- MLP
- CNN
- Deep learning

> [!important]
> Profiled attacks are generally considered the **most powerful form of SCA** because the attacker can learn the leakage behaviour beforehand.

---

# 4. Divide-and-Conquer Attack on AES

AES-128 has a 128-bit key.

Brute-forcing the complete key requires:

$$
2^{128}
$$

which is infeasible.

However, side-channel attacks allow a **divide-and-conquer strategy**.

AES consists of 16 key bytes.

Each byte has:

$$
2^8 = 256
$$

possible values.

Therefore, instead of attacking all 128 bits simultaneously:

1. Attack one key byte.
2. Test all 256 possibilities.
3. Find the best candidate.
4. Repeat for all 16 bytes.

---

## Why attack the first or last AES round?

The first round is attractive because:

- Plaintext is known.
- Only one key byte may need to be guessed.

For example:

$$
SBox(P_i \oplus K_i)
$$

where:

- $P_i$ = known plaintext byte
- $K_i$ = unknown key byte

Only $K_i$ must be guessed.

Complexity:

$$
2^8 = 256
$$

### Attacking deeper rounds

If attacking the second round, additional intermediate values and round-key bytes must be guessed.

The lecture gives an example requiring approximately:

$$
2^{40}
$$

possibilities.

Therefore:

> [!tip]
> **First and last rounds are normally preferred because the number of required key hypotheses is much smaller.**

The last round can similarly be attacked using known ciphertext.

AES key scheduling is deterministic, so recovering a first-round or final-round key can allow recovery of the complete AES key.

---

# 5. CPA Attack Intuition

Suppose we attack one AES key byte.

For every possible key candidate:

$$
k \in \{0,\ldots,255\}
$$

we compute a hypothetical intermediate value:

$$
v = SBox(P_i \oplus k)
$$

Then apply a leakage model such as:

- Hamming Weight
- Hamming Distance

This produces a **hypothetical leakage**.

Compare hypothetical leakage with actual traces using Pearson correlation.

The correct key should produce the strongest dependency.

$$
k^* =
\arg\max_k
|\rho(H_k,T)|
$$

where:

- $H_k$ = hypothetical leakage for key candidate $k$
- $T$ = measured traces
- $\rho$ = Pearson correlation

---

# 6. Leakage Models

Side-channel analysis often requires a model connecting digital computation to physical leakage.

Common models:

## Hamming Weight

Number of `1` bits in a value.

Example:

```text
10110100
```

contains four `1`s.

Therefore:

$$
HW(10110100)=4
$$

## Hamming Distance

Number of bits that change between two values.

$$
HD(x,y)=HW(x\oplus y)
$$

This can model switching activity in digital hardware.

---

# 7. Attack Metrics

Two important metrics are:

## 7.1 Guessing Entropy (GE)

Measures the average rank of the correct key after an attack.

Example ranking:

```text
Candidate 1 -> wrong
Candidate 2 -> wrong
Candidate 3 -> correct
```

The correct key has rank 3.

Ideal case:

$$
GE=0
$$

in the lecture's ranking convention, meaning the correct key is the best-ranked candidate.

Lower GE is better for the attacker.

---

## 7.2 Success Rate (SR)

Probability that the attack successfully ranks the correct key as the best candidate.

Ideal attack:

$$
SR=1
$$

Example:

```text
200 traces -> 80% success
600 traces -> approximately 100% success
```

Attack performance is often plotted against the **number of traces**.

---

# 8. Side-Channel Countermeasures

Two main categories:

1. **Hiding**
2. **Masking**

---

# 9. Hiding

Hiding attempts to make the useful side-channel signal harder to observe.

Two approaches:

## Reduce the signal

Make power/EM activity less dependent on sensitive values.

Example:

- Balanced circuits
- Complementary computation

## Increase the noise

Add unrelated activity so that sensitive leakage becomes harder to distinguish.

Examples:

- Random computations
- Noise generators
- Shuffling
- Timing jitter
- Desynchronization

Conceptually:

$$
\text{SNR}
=
\frac{\text{useful leakage}}
{\text{noise}}
$$

Hiding attempts to reduce this ratio.

---

## Shuffling

Instead of always executing:

```text
SBox0 -> SBox1 -> SBox2 -> SBox3
```

the implementation can randomize execution order:

```text
SBox2 -> SBox0 -> SBox3 -> SBox1
```

The same operation therefore occurs at different time locations between traces.

This makes traces harder to align.

---

## Jitter / Desynchronization

Random timing variations shift leakage points.

The attacker may need:

- Signal processing
- Realignment
- Resynchronization

before applying the attack.

> [!note]
> Hiding usually **increases attack difficulty**, but does not necessarily eliminate leakage.

---

# 10. Masking

Masking is an **algorithm-level countermeasure**.

Instead of directly processing sensitive value $x$, the device processes randomized versions of $x$.

The goal is:

$$
\text{physical leakage}
\not\approx
\text{sensitive value}
$$

Instead:

$$
\text{physical leakage}
\approx
\text{randomized share}
$$

---

# 11. What Is a "Share"?

A **share** is one randomized piece of a sensitive value.

Instead of storing or computing directly with secret:

$$
x
$$

we split it into several shares.

For two Boolean shares:

$$
x = x_0 \oplus x_1
$$

Choose random value:

$$
r
$$

Then:

$$
x_0=r
$$

$$
x_1=x\oplus r
$$

Therefore:

$$
x=(x\oplus r)\oplus r
$$

### Example

Suppose:

```text
x = 1011
r = 0110
```

Then:

```text
Share 1 = r     = 0110
Share 2 = x XOR r = 1101
```

Combining them:

```text
0110 XOR 1101 = 1011
```

which reconstructs $x$.

Individually, each share looks randomized.

---

# 12. Higher-Order Masking

For a masking security order $d$:

$$
\text{number of shares}=d+1
$$

### First-order masking

$d=1$

Two shares:

$$
x=x_0\oplus x_1
$$

### Second-order masking

$d=2$

Three shares:

$$
x=x_0\oplus x_1\oplus x_2
$$

### General case

$$
x=x_0\oplus x_1\oplus\cdots\oplus x_d
$$

---

## d-Probing Security

The intended security model is:

- Attacker observing up to $d$ shares should learn no information about $x$.
- All $d+1$ shares are required to reconstruct information about $x$.

The lecturer compares this to a **jigsaw puzzle**.

Each share is one piece.

Only when all required pieces are combined does the full picture become visible.

---

# 13. Masking Cost and Limitations

Masking has significant implementation cost.

It requires:

- Fresh randomness
- Random number generation
- Extra computation
- Additional storage

The lecture estimates masking may cost at least around **2× computation** in basic cases because both data and mask corrections need to be processed.

### Linear functions

Easy to mask.

Examples in AES:

- XOR
- AddRoundKey
- ShiftRows
- MixColumns

Cost tends to grow approximately linearly with masking order.

### Non-linear functions

Harder to mask.

Main AES example:

- S-box

The S-box cost can grow much faster, approximately quadratically with security order in the lecture's discussion.

---

## Practical masking problems

Security may be reduced by:

- Weak random number generators
- Glitches
- Pipelines
- Compiler optimization
- Power-line coupling
- Accidentally recombining shares
- Reusing masks

Attackers may also perform **higher-order attacks** that combine leakage from multiple shares.

---

# 14. Hiding + Masking

The lecture emphasizes that hiding and masking can complement each other.

Masking reduces dependency on the original sensitive value.

Hiding increases noise or reduces the measurable signal.

Therefore:

$$
\text{Masking + Hiding}
$$

can provide better practical resistance than either alone.

---

# 15. Profiled Side-Channel Attacks

A profiled attack has **two phases**.

## Phase 1 - Profiling / Training

Attacker has a clone device.

The attacker can control:

- Key
- Plaintext
- Measurements

They collect:

```text
Known key + known plaintext -> trace
```

This produces a **labelled dataset**.

The attacker trains a model:

$$
\text{Trace} \rightarrow \text{Sensitive class}
$$

---

## Phase 2 - Attack

Victim device has an unknown key.

The attacker obtains:

```text
Unknown key + known input -> trace
```

The trained model classifies the trace.

Output:

```text
Predicted secret value
```

---

## Easy analogy

Profiling is like learning fingerprints.

During training:

```text
Secret 0 -> leakage pattern A
Secret 1 -> leakage pattern B
Secret 2 -> leakage pattern C
```

During attack:

```text
Unknown leakage looks like pattern B
```

Therefore:

```text
Secret probably = 1
```

---

# 16. Template Attacks

Template attacks are classical profiled attacks.

During profiling:

1. Collect many traces.
2. Group traces according to sensitive value.
3. Calculate statistical properties.

A Gaussian template commonly stores:

- Mean
- Variance / covariance

for each class.

Example:

```text
Key candidate 0 -> distribution 0
Key candidate 1 -> distribution 1
...
Key candidate 255 -> distribution 255
```

During the attack:

1. Collect victim trace.
2. Compare it against templates.
3. Compute likelihood for each candidate.
4. Choose the most likely secret.

Conceptually:

$$
k^*
=
\arg\max_k
P(T_{\text{attack}}\mid k)
$$

With a high-quality template, very few attack traces may be sufficient.

In some cases, even a **single trace** can be enough.

---

# 17. Machine Learning / Deep Learning SCA

Profiled SCA naturally resembles supervised machine learning.

Training data:

$$
(\text{Trace},\text{Label})
$$

Possible models:

- SVM
- Random Forest
- MLP
- CNN
- Deep neural networks

Deep learning can learn more complex and nonlinear relationships than simple statistical templates.

---

# 18. Why Deep Learning Can Defeat Jitter

Jitter shifts the leakage location in time.

Example:

```text
Trace 1:       [LEAKAGE]
Trace 2:          [LEAKAGE]
Trace 3:    [LEAKAGE]
```

Traditional CPA can struggle because traces are not aligned.

CNN-like architectures can learn features with some degree of **shift invariance**.

Therefore, deep learning may identify leakage even when it moves slightly in time.

---

# 19. Why Deep Learning Can Attack Masking

Masked computation splits sensitive information into several shares.

A classical first-order attack may observe only one share and fail.

Deep learning can inspect the **entire trace**.

It may learn to combine leakage corresponding to multiple shares:

$$
x_0,x_1,\ldots,x_d
\rightarrow
x
$$

The lecturer again uses the jigsaw analogy:

> Deep learning may learn where the puzzle pieces are and combine them automatically during training.

---

# 20. Advantages and Disadvantages of Deep-Learning SCA

## Advantages

- Requires fewer attack traces
- Can attack protected implementations
- May work without explicit trace alignment
- May work without manual Point-of-Interest selection
- Can discover complex nonlinear leakage

## Disadvantages

### Black-box nature

If an attack succeeds:

- Why did it succeed?
- Which part of the device leaked?
- What should the designer fix?

may not be clear.

If the attack fails:

- Was the countermeasure strong?
- Was the neural network badly configured?

may also be unclear.

### Hyperparameter problem

Choices include:

- Architecture
- Number of layers
- Kernel sizes
- Learning rate
- Dropout
- Pruning
- Training epochs

There is no universal best configuration.

---

# 21. Portability

A major practical issue in profiled SCA is **portability**.

Suppose:

- $B'$ = training device
- $B$ = victim device

Both are nominally identical devices.

However, their leakage may differ because of:

- Manufacturing variation
- PCB component variation
- Wires/connectors
- Temperature
- Measurement setup
- Device aging
- Probe placement

Portability asks:

> Can knowledge learned from device $B'$ successfully attack a different device $B$?

---

# 22. Same-Device Testing Can Be Misleading

A common experimental mistake is:

```text
Train on Device A
Test on Device A
```

This may cause **overfitting**.

The model learns characteristics specific to that individual device.

A realistic attack is more like:

```text
Train on Device A
Attack Device B
```

The lecture showed substantial degradation when moving between:

- Same device / same key
- Same device / different key
- Different device / same key
- Different device / different key

Therefore:

> [!important]
> Results obtained by training and testing on the same physical device may significantly overestimate real-world attack performance.

---

# 23. Multi-Device Models

One solution is to train on multiple clone devices.

Instead of:

```text
Device A -> model
```

use:

```text
Device A
Device B
Device C
    ↓
combined training
    ↓
robust model
```

The model learns:

- Actual leakage features
- Device-to-device variation

This improves generalization to unseen devices.

The lecture reports **more than 10× improvement** in some experiments.

---

# 24. EM Probe Placement as Portability Problem

EM measurements are sensitive to:

- Probe X/Y position
- Probe distance
- Probe orientation

Removing and replacing a probe slightly changes measurements.

Therefore human placement error creates another form of portability problem.

Multi-device / multi-position training can make models more robust to this variation.

---

# 25. Leakage Analysis vs Leakage Detection

These are different questions.

## Leakage analysis

> **Can the leakage be exploited?**

Usually attempts actual key recovery.

Examples:

- CPA
- Template attack
- Deep-learning attack

## Leakage detection

> **Is any leakage present?**

Does not necessarily recover the key.

Examples:

- SNR
- NICV
- TVLA

---

# 26. Why Leakage Detection Matters

Certification is expensive.

A complete evaluation could require testing:

- SPA
- CPA
- Different leakage models
- Template attacks
- Deep-learning attacks
- Different configurations
- Different countermeasures

The number of attacks continuously increases.

Therefore leakage detection can be used as a **starting point** to determine where further investigation is required.

---

# 27. Signal-to-Noise Ratio (SNR)

A side-channel trace contains:

$$
P_{\text{total}}
=
P_{\text{signal}}
+
P_{\text{noise}}
$$

SNR measures:

$$
SNR =
\frac{\operatorname{Var}(\text{signal})}
{\operatorname{Var}(\text{noise})}
$$

In the lecture:

$$
SNR=
\frac{\operatorname{Var}(E[Y|X])}
{E[\operatorname{Var}(Y|X)]}
$$

where:

- $Y$ = measured trace
- $X$ = value used to classify/group traces

High SNR:

```text
Signal clearly visible
-> easier attack
```

Low SNR:

```text
Signal buried in noise
-> harder attack
```

SNR can help compare:

- Measurement setups
- Leakage models
- Implementations
- Countermeasures

---

# 28. Public Inputs

A **public input** is a value known to the attacker/evaluator.

Examples:

- Plaintext
- Ciphertext

It is different from:

```text
Secret value -> cryptographic key
Public value -> plaintext/ciphertext
```

For example:

```text
P = 00 -> Trace 1
P = 01 -> Trace 2
P = 02 -> Trace 3
```

The plaintext values are public.

The key remains secret.

Public inputs are useful because leakage can sometimes be detected **without knowing the key**.

---

# 29. Normalized Inter-Class Variance (NICV)

NICV is a leakage-detection metric.

Advantages:

- No clone device required
- Uses public parameters
- Does not require the secret key
- Leakage-model agnostic
- Estimates worst-case leakage
- Related to SNR and correlation
- Used in practical side-channel assessment

A form shown in the lecture is:

$$
NICV =
\frac{\operatorname{Var}(E[Y|X])}
{\operatorname{Var}(Y)}
$$

where:

- $Y$ = trace
- $X$ = public input, e.g. plaintext byte

---

## NICV intuition

Suppose different plaintext values cause noticeably different power traces.

Then:

```text
P = 00 -> one leakage distribution
P = 01 -> another leakage distribution
P = 02 -> another leakage distribution
```

If these classes differ significantly, NICV becomes large.

Therefore NICV can identify **where in time the computation depends on processed data**.

---

# 30. What NICV Is Useful For

NICV can identify where AES operations occur in a long trace.

For example:

```text
AddRoundKey
SubBytes
ShiftRows
MixColumns
```

Instead of attacking millions of samples, the evaluator can identify a small window containing the relevant operation.

Example:

```text
Full trace = 1,000,000 samples
NICV identifies SBox0 around samples 20,000-20,600
```

Then CPA only needs to examine that smaller region.

NICV therefore performs **leakage localization**, not direct key recovery.

---

The lecture mentions:

## SOSD

Sum of Squared Differences.

Compare mean traces of different classes.

## SOST

Sum of Squared t-Differences.

A normalized version of SOSD.

## Pearson correlation

If the key is already known, correlation can locate leakage points directly.

# 32. Leakage Assessment

Two broad testing philosophies:

## Evaluation-style testing

Evaluator attempts actual state-of-the-art attacks.

Examples:

- CPA
- Template attacks
- Deep-learning attacks

Advantages:

- Tests exploitability directly

Disadvantages:

- Expensive
- Time-consuming
- Requires expertise
- Attack list is never complete

Used in frameworks such as Common Criteria / FIPS-style evaluation.

---

## Conformance-style testing

Instead of asking:

> Can I recover the key?

ask:

> Can I statistically detect leakage?

Advantages:

- Easier to automate
- Easier to standardize
- Independent of a specific attack

A major example is:

**TVLA**

---

# 33. Test Vector Leakage Assessment (TVLA)

TVLA = **Test Vector Leakage Assessment**

TVLA detects whether two groups of side-channel traces are statistically distinguishable.

Basic idea:

If measurements depend on processed data:

$$
\text{data dependency}
\Rightarrow
\text{side-channel leakage}
$$

TVLA uses **hypothesis testing**.

---

# 34. TVLA Null Hypothesis

Null hypothesis:

$$
H_0:
\mu_1=\mu_2
$$

Meaning:

> The two sets of traces are statistically indistinguishable.

If a statistically significant difference exists:

$$
H_0
$$

is rejected.

This suggests leakage is present.

---

# 35. Fixed-vs-Random (FVR) TVLA

A common TVLA test.

The key $K$ remains fixed.

Collect two datasets.

## Dataset 1 - Random plaintexts

```text
P1
P2
P3
P4
...
```

## Dataset 2 - Fixed plaintext

```text
Pfixed
Pfixed
Pfixed
Pfixed
...
```

If implementation leakage depends on plaintext/intermediate data, the distributions may differ.

Apply Welch's t-test.

---

# 36. TVLA Threshold

The lecture uses:

$$
-4.5 \leq t \leq 4.5
$$

as the acceptance region.

If:

$$
|t| \leq 4.5
$$

the test does not detect statistically significant leakage under that test.

If:

$$
|t| > 4.5
$$

the null hypothesis is rejected and leakage is flagged.

The slides mention high confidence when a sufficiently large number of traces is used.

---

# 37. Important Limitation of TVLA

> [!warning]
> **TVLA detecting leakage does NOT mean a practical key-recovery attack exists.**

TVLA answers:

```text
Is measurable leakage present?
```

It does **not** answer:

```text
Can I recover the cryptographic key?
```

Therefore:

```text
TVLA fail
      ↓
Leakage detected
      ↓
May investigate with CPA/template/DL attack
      ↓
Determine exploitability
```

Similarly, passing one TVLA test does not prove absolute side-channel security.

---

# 38. Other TVLA Variants

Besides Fixed vs Random:

- Fixed vs Fixed
- Random vs Random
- Fixed vs Semi-Random
- Other application-specific tests

TVLA is essentially a **pass/fail leakage-detection methodology**.

# 39. Post-Quantum Cryptography (PQC)

Moving to post-quantum cryptography does **not** eliminate side-channel attacks.

PQC algorithms are designed to resist attacks from quantum computers.

However, they still run on physical hardware:

- Microcontrollers
- Phones
- PCs
- Servers
- CPS devices

Therefore they can still produce:

- Power leakage
- EM leakage
- Timing leakage

> [!important]
> **Mathematical quantum resistance is different from implementation security.**

---

# 40. NIST PQC Algorithms Mentioned

Examples mentioned include:

### Key Encapsulation Mechanism

- Kyber

### Digital signatures

- Dilithium
- FALCON
- SPHINCS+

The lecture mainly focuses on attacking **Kyber-style lattice-based KEMs**.

# 41. Key Encapsulation Mechanism (KEM)

Purpose:

> Allow two parties to establish a shared session key over an untrusted channel.

Simplified process:

```text
Alice:
    Generate public key pk
    Generate secret key sk

Alice -> Bob:
    pk

Bob:
    Use pk to encapsulate
    Produce ciphertext ct
    Produce shared key K

Bob -> Alice:
    ct

Alice:
    Decapsulate ct using sk
    Recover shared key K
```

Afterward both parties have:

$$
K
$$

and can use a symmetric cipher such as AES.

---

# 42. Why the Long-Term Secret Key Matters

Alice may reuse one public/secret key pair for many sessions.

If an attacker recovers Alice's long-term secret key:

$$
sk
$$

many session keys may become compromised.

Therefore the **decapsulation procedure** is an important attack target.

---

# 43. Chosen-Ciphertext Attack

A malicious attacker sends specially constructed ciphertexts to Alice.

Goal:

> Cause internal decryption behaviour that reveals information related to the secret key.

Conceptually:

```text
Attacker
   |
handcrafted ciphertext
   |
   v
Decapsulation using secret key
   |
secret-dependent internal message
```

A theoretical plaintext-checking oracle would reveal information such as:

```text
Did ciphertext decrypt to M0 or M1?
```

Repeated queries can produce equations about the secret key.

---

# 44. Fujisaki-Okamoto (FO) Transform

CCA-secure schemes protect against direct chosen-ciphertext attacks.

Simplified decapsulation:

```text
Ciphertext
    ↓
Decrypt using secret key
    ↓
Message
    ↓
Re-encrypt
    ↓
Compare with original ciphertext
    ↓
Valid key OR abort/random key
```

An invalid ciphertext is not supposed to reveal its decrypted message.

Mathematically, this protects against the attacker observing internal plaintext directly.

---

# 45. Why Side Channels Break the Assumption

Even if the internal message is never returned to the attacker:

> **The device still computed it.**

If it was computed, it may create:

- Power leakage
- EM leakage
- Timing leakage

Therefore:

```text
Internal secret-dependent computation
          ↓
Physical leakage
          ↓
Side-channel oracle
```

An attacker may reconstruct the information that the mathematical protocol intended to hide.

---

# 46. Side-Channel Assisted Plaintext-Checking Oracle

The attacker crafts ciphertexts so that an internal value has only a small number of possible states.

For example:

```text
M = 0
or
M = 1
```

Then collect templates:

```text
M = 0 -> Template T0
M = 1 -> Template T1
```

For an unknown trace:

```text
Trace -> compare against T0 and T1
```

If closer to:

```text
T0 -> infer M = 0
T1 -> infer M = 1
```

This converts side-channel leakage into a plaintext-checking oracle.

Repeated queries can eventually reveal secret-key coefficients.

# 47. Leakage Amplification by Hashing

A useful observation from the lecture:

Two internal messages may differ by only one bit.

A hash function has an avalanche property:

```text
tiny input difference
      ↓
large output difference
```

Therefore:

$$
M_0 \approx M_1
$$

may become:

$$
Hash(M_0)
\not\approx
Hash(M_1)
$$

This can amplify side-channel differences in later computations.

Thus later operations may provide stronger leakage than the original difference.

Traditional physical attacks assumed:

Attacker physically possesses device

and measures:

- Power

- Cloud servers

# 50. Why Microarchitectures Leak

Three major reasons:

## Sharing

Multiple programs share hardware resources:

- Caches
- Branch predictors
- TLBs
- Execution ports

One program can leave hardware state behind for another program to observe.

## Optimization

Modern CPUs are optimized for speed.

Examples:

```text
Cache hit  -> fast
Cache miss -> slow
Correct prediction -> fast
Misprediction -> slower
```

Timing therefore depends on previous activity.

## Observability

Programs can measure time using:

- Cycle counters
- Timer APIs
- Counting loops

Therefore:

$$
\text{secret-dependent behaviour}
+
\text{measurable timing difference}
=
\text{side channel}
$$

---

# 51. Cache Timing

Suppose:

```c
t0 = timer();
access(addr);
t1 = timer();
```

Calculate:

$$
\Delta t = t_1-t_0
$$

Example:

```text
70 cycles  -> cache hit
300 cycles -> RAM access/cache miss
```

Therefore the attacker can infer whether a particular address was recently accessed.

---

# 52. CPU Cache Hierarchy

Conceptually:

```text
CPU Core
  |
 L1 Cache   -> smallest / fastest
  |
 L2 Cache
  |
 L3 Cache   -> larger / often shared
  |
 RAM        -> much slower
```

Important property:

- L1/L2 may be private to a core.
- Last-level cache such as L3 may be shared.

Therefore one core can sometimes infer activity occurring on another core through shared cache state.

---

# 53. Secret-Dependent Memory Access

Suppose victim code contains:

```text
if secret_bit == 1:
    access table[A]
else:
    access table[B]
```

Attacker does not directly see `secret_bit`.

Instead the attacker asks:

```text
Was table[A] cached?
or
Was table[B] cached?
```

If `A` is cached:

```text
secret_bit = 1
```

If `B` is cached:

```text
secret_bit = 0
```

Therefore secret-dependent addresses create timing leakage.

> [!important]
> Constant-time programming aims to eliminate secret-dependent branches and secret-dependent memory accesses.

---

# 54. Flush+Reload

Flush+Reload consists of four stages.

## 1. Flush

Remove a target cache line.

## 2. Wait

Allow victim to execute.

## 3. Reload

Access the same address again.

## 4. Measure

If reload is fast:

```text
Victim accessed it
-> line returned to cache
```

If reload is slow:

```text
Victim probably did not access it
```

### Strength

- Very high resolution
- Can monitor individual cache lines
- Low noise

### Weakness

Requires:

- Shared memory
- Ability to flush relevant cache lines

---

# 55. Prime+Probe

Prime+Probe does not require the same shared memory page.

## 1. Prime

Fill a cache set with attacker-controlled data.

## 2. Wait

Let victim run.

Victim may evict attacker's cache lines.

## 3. Probe

Attacker re-accesses its own cache lines.

## 4. Measure

Slow access indicates eviction.

Therefore:

```text
slow
-> victim used same cache set
```

### Advantages

- Can work across cores
- Can work across virtual machines

### Disadvantage

- Lower spatial resolution
- Noisier than Flush+Reload

---

# 56. Cache Attack on RSA

Recall square-and-multiply:

```text
Every bit -> Square
Bit = 1   -> extra Multiply
```

Square and multiply routines occupy different memory addresses.

Attacker monitors the multiply routine.

If multiply code was accessed:

```text
key bit = 1
```

If not:

```text
key bit = 0
```

This is conceptually the same attack as SPA, except:

```text
SPA:
observe power signature

Cache attack:
observe memory/cache activity
```

---

# 57. Cache Attack on AES

High-performance AES implementations may use lookup tables such as T-tables.

Lookup address can depend on:

$$
P_i\oplus K_i
$$

where:

- $P_i$ is known plaintext
- $K_i$ is secret key byte

By observing which table regions are accessed over many encryptions, attackers can eliminate incorrect key hypotheses.

This is analogous to CPA:

```text
Known plaintext
+
secret-dependent behaviour
+
many observations
=
key-byte inference
```

# 58. Spectre and Meltdown

Both involve **transient execution**.

Transient execution means:

> An instruction executes internally but its architectural result is later discarded.

However, side effects such as cache state may remain.

---

# 59. Spectre

Modern CPUs perform **speculative execution**.

The processor predicts which branch will execute.

Example:

```text
if condition:
    operation A
else:
    operation B
```

CPU may guess `operation A` before the condition is fully resolved.

If wrong:

- Architectural result is discarded.
- But cache changes caused by speculative execution may remain.

Spectre exploits these remaining microarchitectural effects.

Simplified:

```text
Train branch predictor
      ↓
CPU speculates incorrectly
      ↓
Secret-dependent access occurs transiently
      ↓
Architectural result discarded
      ↓
Cache footprint remains
      ↓
Attacker measures cache
```

---

# 60. Meltdown

Meltdown involves transient access to memory that should not be accessible to a process.

Simplified:

```text
CPU transiently reads protected memory
      ↓
Permission violation eventually detected
      ↓
Instruction result discarded
      ↓
Cache side effect remains
      ↓
Attacker reconstructs information
```

Thus architectural security checks may occur too late to prevent microarchitectural information leakage.

---

# 61. Software-Based Power Measurement

Power attacks are not necessarily limited to physical oscilloscopes.

Modern processors contain internal power-monitoring interfaces.

Example:

**Intel RAPL**

RAPL = Running Average Power Limit.

It monitors power/energy usage for components such as:

- CPU package
- Memory
- GPU
- Cores/cache depending on platform

Software can read these measurements.

---

# 62. PLATYPUS Attack

PLATYPUS demonstrated that software-accessible energy measurements can become a side channel.

Instead of:

```text
Oscilloscope + physical probe
```

the attacker can potentially use:

```text
software-accessible energy sensor
```

The lecture notes that RAPL is far lower resolution than a laboratory oscilloscope, but some computations produce sufficiently strong aggregated leakage.

Research has demonstrated leakage related to:

- Instructions
- Operand Hamming weights
- Memory activity
- Cryptographic computations

The general lesson is:

> **A sensor designed for performance or energy monitoring can accidentally become a security side channel.**

# 63. Hardware Performance Counters

Modern CPUs have a Performance Monitoring Unit (PMU).

Performance counters can directly measure events such as:

- Cache misses
- Branch mispredictions
- TLB activity
- Execution-port activity

Instead of manually determining:

```text
cache hit vs cache miss
```

using timing, a performance counter may already report that information.

This creates both:

### Offensive uses

Attackers can infer sensitive activity.

### Defensive uses

Security systems can monitor abnormal events that may indicate attacks.

Access is therefore commonly controlled through system privileges.

# 64. Microarchitectural Mitigations

Mitigation can occur at three levels.

---

## Software-level

Avoid:

- Secret-dependent branches
- Secret-dependent memory addresses

Possible techniques:

- Constant-time programming
- Bitslicing
- AES-NI
- Montgomery ladder
- Key/exponent blinding
- Constant-time verification tools

---

## System / OS-level

Possible mitigations:

- Disable SMT for sensitive workloads
- Cache partitioning
- Page colouring
- Disable memory deduplication
- Kernel page-table isolation (KPTI)
- Reduce timer resolution
- Restrict access to RAPL
- Restrict performance counters

---

## Hardware-level

Possible mitigations:

- Randomized cache mapping
- Partitioned/per-domain caches
- Speculation barriers
- Microcode/firmware updates
- Constant-time instructions
- Filtering of power-monitoring interfaces

---

# 65. Security vs Performance Trade-Off

Many microarchitectural vulnerabilities arise because modern processors maximize performance through:

- Sharing
- Caching
- Speculation
- Out-of-order execution
- Monitoring interfaces

Security mitigations often reduce these optimizations.

Therefore:

$$
\text{More isolation/security}
\leftrightarrow
\text{Potential performance cost}
$$

This trade-off appears repeatedly in system security.

# 68. Important Comparisons

## Hiding vs Masking

| Hiding | Masking |
|---|---|
| Hides physical signal | Randomizes sensitive data |
| Reduce signal | Split data into shares |
| Increase noise | Uses fresh randomness |
| Shuffling/jitter | Boolean/arithmetic masking |
| Usually raises attack effort | Has a stronger formal security basis |
| Does not necessarily remove leakage | Higher-order attacks may still work |

---

## Non-Profiled vs Profiled Attack

| Non-Profiled | Profiled |
|---|---|
| No clone/training device | Clone/training device available |
| Uses assumed leakage model | Learns leakage from measurements |
| Example: CPA | Example: Template/DL attack |
| Often requires more attack traces | Can require very few victim traces |
| Hamming Weight/Distance models | Statistical/ML classifier |

---

## Leakage Detection vs Leakage Analysis

| Leakage Detection | Leakage Analysis |
|---|---|
| "Is leakage present?" | "Can I exploit it?" |
| Does not require key recovery | Attempts secret/key recovery |
| SNR | CPA |
| NICV | Template attacks |
| TVLA | Deep-learning attacks |

---

## NICV vs TVLA

| NICV | TVLA |
|---|---|
| Measures/localizes leakage | Hypothesis-based leakage test |
| Uses public inputs | Compares two trace populations |
| No secret key required | Key may remain unknown |
| Produces leakage score | Pass/fail-style threshold |
| Useful for finding Points of Interest | Useful for conformance testing |

---

## SPA vs Cache Attack

| SPA | Cache Attack |
|---|---|
| Observe power/EM differences | Observe cache/timing differences |
| Usually physical access | Can be remote/shared-machine |
| Example: square vs multiply | Example: multiply routine cached or not |
| Physical leakage | Microarchitectural leakage |

# 69. Key Terms

### Side channel
Unintended observable information produced by computation.

### Trace
A sequence of side-channel measurements over time.

### Leakage
Statistical dependency between measurements and processed data.

### Leakage model
Model predicting physical leakage from intermediate digital values.

### Share
A randomized piece of a sensitive value used in masking.

### Masking order
For order $d$, sensitive data is represented using $d+1$ shares.

### Profiling
Learning leakage behaviour using a controlled training device.

### Template attack
Profiled attack using statistical distributions for each sensitive class.

### Public input
Known non-secret value such as plaintext or ciphertext.

### Point of Interest (PoI)
Region/sample of a trace containing useful leakage.

### Portability
Ability of a trained attack model to transfer from one physical device to another.

### SNR
Ratio of exploitable signal variance to noise variance.

### NICV
Model-agnostic metric used to identify data-dependent leakage.

### TVLA
Statistical leakage-assessment methodology based on hypothesis testing.

### Fixed-vs-Random
TVLA test comparing traces for fixed input against traces for random inputs.

### Cache hit
Requested data is already cached -> fast.

### Cache miss
Data must be fetched from slower memory -> slow.

### Flush+Reload
Remove cache line, allow victim to run, then time its reload.

### Prime+Probe
Fill cache set, allow victim to run, then measure which lines were displaced.

### Transient execution
Instruction executes internally but its architectural result is later discarded.

# 71. Very Short Memory Summary

If only remembering a few ideas:

1. **Secure crypto can leak through implementation.**
2. **SCA measures physical effects such as power, EM or timing.**
3. **AES can be attacked byte-by-byte rather than guessing the whole key.**
4. **Hiding obscures leakage; masking randomizes sensitive data.**
5. **A share is one randomized component of a masked sensitive value.**
6. **Profiled attacks train on a known-key clone device and attack an unknown-key device.**
7. **Portability asks whether that trained model works on another physical device.**
8. **SNR/NICV/TVLA detect or quantify leakage; they do not necessarily recover the key.**
9. **TVLA commonly uses a fixed-vs-random Welch t-test with a ±4.5 threshold.**
10. **Post-quantum crypto can still suffer implementation side channels.**
11. **Microarchitectural attacks use shared CPU state such as caches instead of physical probes.**
12. **Flush+Reload and Prime+Probe infer what memory the victim accessed.**
13. **Spectre/Meltdown exploit transient execution effects.**
14. **Even built-in sensors such as RAPL can become side channels.**
15. **Implementation security is as important as mathematical cryptographic security.**
